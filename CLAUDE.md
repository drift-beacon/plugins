# Plugins Repository

Standalone plugins for Drift Beacon, built on the `@drift-beacon/plugin` SDK.

## Layout

A pnpm workspace with one lockfile at the root. Each plugin is one package:

```
plugin-name/
  package.json       # dependencies for main and UI; scripts dev / build / release
  vite.config.ts     # plugins: [react(), tailwindcss(), driftBeacon()]
  tsconfig.json      # references .drift-beacon/tsconfig.{main,ui}.json
  manifest.json      # id, name, version, apiVersion, icon, configuration, …
  main/src/index.ts  # server side, run in a plugin host: export default definePlugin({ onStart(ctx) { … } })
  ui/index.html      # browser UI, a Vite app (root ui/) loaded in a sandboxed iframe
  ui/src/main.tsx    # await connect(), then render
  ui/public/icon.png # the manifest icon ("icon": "icon.png"), plus any static files
  .drift-beacon/     # generated by dbplugin prepare, self-gitignored: config.d.ts and the two tsconfigs
  dist/              # vite build output, exactly the release package
  releases/<id>.zip  # written by pnpm release
```

`dist/` holds `manifest.json`, `package.json`, `main/index.js`, `ui/index.html`, `ui/assets/…` and `ui/icon.png`, plus a `.drift-beacon-dev.json` marker for the server that is never packed. `driftBeacon()` owns `root`, `base` and `build.outDir`: don't set them in `vite.config.ts`. It builds main as a single file with `@drift-beacon/plugin` external (the app supplies the SDK at run time) and every other dependency bundled.

A plugin may also carry `shared/` (the contract main, the UI and the tests import; bundled into both), `tests/*.test.mjs` (`pnpm test`) and a `DESIGN.md`. cartridge-player adds `player/`: the Arduino firmware of the physical player, with host-testable C++ in `player/src/core` and its setup page in `player/portal/` (generated into `player/src/portal_page.h` by `pnpm portal`). `tests/` and `player/` are not part of `dist/` or the release zip.

Don't name a script `prepare`: pnpm runs it on install.

## Setup

`pnpm install`. Each plugin's postinstall runs `dbplugin prepare`.

## SDK

`@drift-beacon/plugin` is a dev dependency. It also provides the `dbplugin` CLI and `driftBeacon()` (`@drift-beacon/plugin/vite`).

- **Main:** `import { definePlugin } from "@drift-beacon/plugin"`.
- **UI:** `import { connect } from "@drift-beacon/plugin/ui"`. The UI bundles this small client. Use any UI framework and libraries at any version.
- `manifest.json` `apiVersion` is the plugin API version the plugin is built for (`"0.2"` today). `pnpm dev`, `pnpm build` and `pnpm release` stop unless the installed SDK supports it (before 1.0, an exact match), and Drift Beacon won't run a plugin built for a version it doesn't support: it shows it as incompatible instead.
- **Typed declarations, no generics:** `dbplugin prepare` writes `.drift-beacon/config.d.ts` from manifest configuration and `provides`, typing `ctx.config`, command handlers, emitted events and published state. Peers listed in `uses` are not typed from their manifests. It runs on install and on every `pnpm dev` start, `pnpm build` and `pnpm release`, and a running `pnpm dev` reruns it when manifest.json changes; otherwise run `pnpm exec dbplugin prepare` after editing `configuration`.
- **Icons:** activities and categories carry `iconPath`, the SVG path data for `icon` (viewBox `0 0 24 24`, draw with `fill`), or `null` when `icon` isn't a known MDI icon. Draw it with the plugin's `ui/src/components/Icon.tsx` (`<Icon path={activity.iconPath} color={activity.color} className="h-4 w-4" />`) or feed it to your own renderer. Never resolve `icon` names yourself.

## Main `ctx`

```ts
export default definePlugin({
  onStart(ctx) {
    ctx.mqtt.subscribe(ctx.config.mqttTopic, ({ payload }) => {
      /* … */
    });
    ctx.sessions.onStarted((session) => {
      /* a user just started a session */
    });
    ctx.routes.post("webhook", async ({ body }) => ({ status: 202, body: { ok: true } }));
  },
});
```

- `ctx.plugin`, `ctx.user`, `ctx.workspace`, `ctx.config` (validated, defaults applied; a change restarts the instance).
- `ctx.activities` / `ctx.categories` / `ctx.sessions`: `list(filter?)`, `get(id)`, and `sessions.live({ mine? })`. `activities.list({ categoryId?, trackingType?, includeArchived? })` is sorted like the app's Activities page and hides archived activities unless `includeArchived: true`; `categories.list()` is sorted; `sessions.list({ activityId?, status?, mine? })` is newest first. Group by category with `ctx.categories.list()` and `category.activities()` rather than your own sorting helpers.
- They return frozen **models** that read the latest data the app sent: the row's fields (an activity's `color` is already resolved, and so is `iconPath`; `startedAt`/`endedAt` are `Date`s, don't mutate them) plus links and actions, e.g. `activity.category`, `activity.isLive` (the current user), `activity.track()` (start a span, mark a point), `activity.end()`, `category.activities()`, `session.activity`, `session.isMine`, `session.duration()`. A model keeps its identity; `model.data` is the plain row, a new object whenever it changes. A removed row's model has `exists: false`.
- `ctx.sessions.start / end / mark / discard`, and the models' `start`, `mark`, `track`, `end`, `discard`: actions, run as `ctx.user`. They resolve with the session once `ctx` shows the result, and reject with a `PluginError` (check `error.code`).
- **Live events** — `sessions.onStarted`, `onEnded(session, "completed" | "discarded")`, `onMarked`, with a `Session` model (check `session.isMine`): something just happened. Never fired for sessions that arrive later from a device's offline sync. They may run before or after the code awaiting the action that caused them.
- **Data events** — `activities/categories/sessions.onChange(change)` (`added` / `updated` with the plain `previous` row / `removed`; `item` is the model) and `onDataChange()`: the data is different now, possibly because of a sync burst. Don't use them to trigger actions.
- `ctx.storage`: `get` (sync), `set`/`remove` (optimistic), `keys`, `onChange`. JSON values, per user and workspace, shared with the UI.
- `ctx.mqtt`: `subscribe(filter, cb)`, `publish` (rejects without a broker), `status`, `onStatusChange`.
- `ctx.routes.get/post(name, handler)`: served at `<ctx.plugin.apiPath>/<name>` with a workspace API key; handlers return `{ status?, body? }`. Credentials are never passed to the handler.
- `ctx.commands.handle(name, handler)` and `ctx.plugins.get(manifestId).command(name, input, { timeoutMs })`: commands between plugins, as the same user in the same workspace. Declare them in `manifest.json` (`provides.commands`, with JSON-schema-subset `input`/`output`) and list the plugins you run commands on in `uses` with a version range. Example: magic-cube provides `selectPreset`; cartridge-player runs it from `POST <apiPath>/cube-preset { preset }`. Errors: `not-installed`, `disabled`, `incompatible`, `unavailable` (didn't run), `timeout`/`stopped` (may have run), `loop` (a chain deeper than 8).
- `ctx.ui.handle(name, handler, { input? })`, `ctx.ui.post(name, payload?, { to? })`, `ctx.ui.clients` and `ctx.ui.onClientsChange(cb)`: the private channel to the plugin's own UI (SDK 0.2.4). Nothing is declared in `manifest.json`, so other plugins and Home Assistant can't reach it. Declare a command only when something other than your own UI should run it; type the channel in a `shared/ui-channel.ts` that main and UI both import (nanoleaf and cartridge-player do).
- Main provides `ctx.events.emit(name, payload)` and `ctx.state.set/get` for names declared in `provides`. Its own peer and peers in `uses` expose status, state and `onEvent`. State lasts only while the provider runs; events are transient. Keep event-driven command reactions in main so chain limits apply.
- `ctx.log.info/warn/error`, `ctx.onStop(fn)`.

Everything registered through `ctx` stops when the instance stops. Each plugin has one instance per enabled user/workspace, and its module is shared between those instances: keep state inside `onStart`, not at module scope.

## UI `ctx`

`const ctx = await connect()` performs the handshake. The UI receives identity, config, data, session actions, storage and data events, plus `ctx.plugins` for itself and plugins declared in `uses`. It has no MQTT, routes, logs or live session-event API. To reach its own main code it uses the private channel (SDK 0.2.4): `ctx.main.request(name, input, { timeoutMs, signal })`, `ctx.main.onMessage(name, cb)` and `ctx.main.onResync(cb)`. `ctx.plugins.self.command(…)` runs a declared command, which is public API.

- Peer status and state are coalesced over about 250 ms. A command's effects can arrive before or after its response; render from state listeners or use the command output.
- UI SDK 0.2.1 supports `peer.onEvent(name, callback)`. Events arrive after the peer state published before them and do not trigger `ctx.onDataChange`. They are not replayed; disconnects, reloads and the bounded server buffer can lose them. Older app/hub versions never deliver them.
- Every open UI copy receives peer events. A command started by a UI listener begins a new chain, so listeners should render; put event-driven command reactions in main to avoid loops across open interfaces. UI listener errors are logged, not treated as main-code faults.
- Re-render model views with `ctx.onDataChange` (for React, use `useSyncExternalStore`; each example's `ui/src/drift-beacon.ts` has `useDriftBeacon()`). Lists retain identity until their cache is invalidated by workspace data changes. Models retain identity while `model.data` changes, so key `React.memo`/`useMemo` on the data needed by the component, not only the model object.

## Commands

In a plugin folder:

```bash
pnpm dev       # vite: the UI with HMR; main is rebuilt on save and Drift Beacon applies it
pnpm build     # vite build: production build of main and UI into dist/
pnpm release   # dbplugin pack: typecheck, build fresh in a temp folder, write releases/<id>.zip and print its JSON; dist/ is untouched
pnpm exec tsc -b   # typecheck main and UI
pnpm test      # node --test tests/*.test.mjs (Node strips the types); cartridge-player's also needs a C++17 compiler (CXX picks one)
```

In cartridge-player, `pnpm portal` regenerates the firmware's setup page header after editing `player/portal/`, and `arduino-cli compile --profile s3zero player` builds the firmware (see `cartridge-player/player/README.md`).

From the root, `pnpm -r build` builds every plugin. Automation that parses pack output uses `pnpm exec dbplugin pack`, because `pnpm release` prints a script banner before the JSON.

## Releases

Drift Beacon offers the `version` in each `manifest.json` on `main` and installs the GitHub release tagged `<id>-<version>`, whose `<id>.zip` must hold an equal manifest. To release a plugin, bump `version` in its manifest and push to `main`.

- `.github/workflows/release.yml` runs on every push to `main` (and from **Run workflow**). It publishes each advertised version that has no release yet, one job per plugin: its tests, `dbplugin pack`, then `gh release create` with the tag at that commit. Only the newest commit of `main` publishes.
- `.github/workflows/validate.yml` runs on pull requests and `main`: the script tests, `plugin-release.mjs check`, every plugin's tests and a pack of every plugin.
- `scripts/plugin-release.mjs` holds the logic (`check`, `pending`, `publish`). `node scripts/plugin-release.mjs check` runs anywhere and says which advertised versions are published.

A published version never changes. Releases are immutable, and servers refuse a release whose manifest differs from the one on `main`, so any edit to `manifest.json` needs a new `version` (`check` fails without it), and so does the fix for a bad release. Don't create or move `<id>-<version>` tags by hand: publishing creates them.

Drift Beacon reads development plugins from `DEV_PLUGINS_PATH` (this folder) and loads each plugin's `dist/`. Run its server in development mode with `DEV_PLUGINS_PATH` set to this folder, then `pnpm dev` in a plugin folder:

- Saving main code rebuilds `dist/main/index.js` (with a source map); the server notices and restarts only that plugin's host. Settings, storage and data are kept, and a save that changes nothing in the build restarts nothing (`main built in N ms · no changes`).
- Saving UI code updates the plugin's iframe in the web app through Vite HMR (the server tells the web app the dev URL).
- Editing `manifest.json` re-validates it, copies it into `dist/` and regenerates `.drift-beacon/config.d.ts`; an invalid manifest is reported and the last valid one stays. `ui/public/<icon>` is kept in `dist/ui/`.
- A development plugin is registered as `<manifest id>-dev` (for example `magic-cube-dev`), with its own enablement, settings and storage. While it is enabled in a workspace, it replaces an installed copy of the same plugin there: other plugins, Home Assistant and the installed copy's routes reach the development build, and the installed copy runs again when you disable the development build.
- The server connects to `pnpm dev` and prints `[beacon]` lines in its terminal: `✓ connected to Drift Beacon`, `✓ runtime restarted in N ms · running in Home`, `↻ Replaces installed … while this build is enabled`, the plugin's logs and faults per workspace (source-mapped to `main/src`), and status changes. If no server connects within 5 s, `pnpm dev` says how to start one.

Without `pnpm dev`, a `pnpm build` is applied automatically too (it restarts the plugin's runtime even when only the UI changed); Rescan and Reload runtime are fallbacks. Don't run `pnpm build` while `pnpm dev` runs in the same folder: the next dev save takes `dist/` back.
